# Copilot Instructions: datetime-local Timezone Handling

## Overview
The HTML `datetime-local` input type is timezone-agnostic - it sends values like "2025-10-01T20:30" without timezone information. This creates a common web development challenge: how does the server know if this time is UTC, user's local time, or something else?

## The Problem
- **Client sends**: `"2025-10-01T20:30"` (no timezone info)
- **Server receives**: A string that could mean different things
- **Without context**: Server interprets using its own timezone (usually wrong)
- **Data corruption**: Times get shifted incorrectly in database

## Core Solutions Pattern

### 1. JavaScript Enabled (Automatic Detection)
```javascript
// Detect user's timezone
const timezone = Intl.DateTimeFormat().resolvedOptions().timeZone;
// Result: "America/New_York", "Europe/London", etc.

// Send with form as hidden field
<input type="hidden" name="timezone" value={timezone} />
```

### 2. JavaScript Disabled (Manual Selection)
```html
<!-- Only shown when JavaScript is disabled -->
<noscript>
  <select name="timezone">
    <option value="UTC">UTC</option>
    <option value="America/New_York">Eastern Time</option>
    <option value="Europe/London">London Time</option>
    <!-- etc... -->
  </select>
</noscript>
```

### 3. Server-Side Handling
```javascript
// Handle all scenarios
if (!timezone || timezone === 'Unknown (JavaScript required)') {
  // No timezone info: treat as UTC
  dateObject = new Date(submittedValue + 'Z');
} else if (timezone === 'UTC') {
  // UTC selected: force UTC parsing
  dateObject = new Date(submittedValue + 'Z');
} else {
  // Timezone available: treat as local time
  dateObject = new Date(submittedValue);
}
```

## Implementation Guidelines

### Frontend Patterns
1. **Hydration-Safe State Management**:
   ```javascript
   const [timezone, setTimezone] = useState('Unknown (JavaScript required)');
   
   useEffect(() => {
     setTimezone(Intl.DateTimeFormat().resolvedOptions().timeZone);
   }, []);
   ```

2. **UTC to Local Conversion for Input**:
   ```javascript
   // Convert UTC datetime to local for datetime-local input
   const localTime = new Date(utcDate.getTime() - utcDate.getTimezoneOffset() * 60000);
   const formatted = localTime.toISOString().slice(0, 16);
   ```

3. **Progressive Enhancement Structure**:
   ```html
   <!-- Always include timezone field -->
   <input type="hidden" name="timezone" value={detectedTimezone} />
   
   <!-- Fallback for no JavaScript -->
   <noscript>
     <select name="timezone">
       <!-- timezone options -->
     </select>
   </noscript>
   ```

### Backend Patterns
1. **Consistent UTC Storage**:
   - Always store dates in UTC in database
   - Convert to UTC before saving
   - Convert from UTC when displaying

2. **Timezone Handling Logic**:
   ```javascript
   function parseDateTime(dateString, timezone) {
     if (!timezone || timezone === 'Unknown (JavaScript required)') {
       return new Date(dateString + 'Z'); // Force UTC
     }
     if (timezone === 'UTC') {
       return new Date(dateString + 'Z'); // Force UTC
     }
     return new Date(dateString); // Local time interpretation
   }
   ```

## Alternative Approaches

### Cookie-Based Solution
- Set timezone in cookie on first visit
- Read server-side for subsequent requests
- Pros: Works server-side, persistent
- Cons: Cookie management, first-visit issue

### IP Geolocation
- Estimate timezone from user's IP
- Pros: Works without JavaScript
- Cons: Inaccurate with VPNs, privacy concerns

### URL Parameters
- Pass timezone as query parameter
- Pros: Simple, cacheable
- Cons: Ugly URLs, requires user action

### Two-Pass Rendering
- Render with server defaults first
- Update with client timezone on hydration
- Pros: Progressive enhancement
- Cons: Potential layout shift

## Best Practices

1. **Always Default to UTC**: When in doubt, treat ambiguous times as UTC
2. **Progressive Enhancement**: Ensure basic functionality works without JavaScript
3. **Clear User Communication**: Show what timezone will be used
4. **Consistent Storage**: Always store UTC in database
5. **Test Both Scenarios**: Verify behavior with and without JavaScript
6. **Graceful Fallbacks**: Have a clear strategy when timezone is unknown

## Common Pitfalls

1. **Server Timezone Assumption**: Don't let server interpret times in its own timezone
2. **Hydration Mismatches**: Server and client render different timezones initially
3. **Missing Fallbacks**: Not handling JavaScript-disabled scenarios
4. **Inconsistent Storage**: Mixing UTC and local times in database
5. **User Confusion**: Not explaining what timezone is being used

## Framework-Specific Notes

### React Router
- Use loaders for server-side UTC data
- Use actions for form submission handling
- Implement hydration-safe state management

### Next.js
- Handle in API routes or server actions
- Use client components for timezone detection
- Consider server components for UTC defaults

### SvelteKit
- Use form actions for server-side handling
- Implement progressive enhancement patterns
- Use stores for client-side state

## Testing Strategy

3. **Different Timezones**: Test with various user timezones
4. **Edge Cases**: Test with UTC, unknown timezones
5. **Database Consistency**: Verify all times stored as UTC
